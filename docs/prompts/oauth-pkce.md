# Задача: OAuth 2.0 авторизация (Authorization Code + PKCE) через Keycloak + PostgreSQL

## Цель
Добавить в FitLog аутентификацию и авторизацию: Keycloak как Identity Provider (данные в собственном PostgreSQL), backend (ASP.NET Core) валидирует JWT, клиент (Expo: Android, web) входит по Authorization Code + PKCE.

Вход обязательным не является: в приложение можно зайти **гостем** без авторизации, но часть функций при этом недоступна и требует входа.

## Контекст
Прочитай перед началом: `CLAUDE.md`, `backend/CLAUDE.md`, `backend/docs/architecture.md`, `frontend/CLAUDE.md`, `frontend/docs/architecture.md`. Пункты «Аутентификация и авторизация» и «Аутентификация и защита маршрутов» там числятся открытыми решениями. Эта задача их закрывает, после реализации обнови соответствующие разделы документов.

## Порядок работы
1. Сначала войди в plan mode и предложи план: этапы, затрагиваемые файлы, риски. Не пиши код до моего согласования плана.
2. Список функций «доступно гостю» / «только после входа» пока не готов. Вместо него делаем один тестовый блок (см. «Гостевой режим»). Реальное разделение функций вне объёма этой задачи.
3. Реализуй по этапам: (A) Keycloak, (B) backend, (C) frontend. После каждого этапа остановись и дай шаги ручной проверки.

## Гостевой режим (сквозное требование)
- Приложение открывается без входа. Экран входа не блокирует запуск: пользователь выбирает «Войти» или «Продолжить как гость».
- **Тестовый блок вместо списка функций.** На главном экране один блок (например, `AuthOnlyBlock`), который показывает контент только авторизованному пользователю: приветствие с email из `GET /users/me` (так проверяется весь путь токен → backend → профиль). Гостю на его месте показывается заглушка «Требуется вход, чтобы использовать эту функцию» с кнопкой «Войти». Остальное приложение доступно гостю как есть.
- Блок реализуется через общий механизм (`AuthGate` в `shared/`, см. этап C), чтобы позже его можно было переиспользовать для настоящих функций без переделки.
- Если для блока нужен backend-эндпоинт, это `GET /users/me`, отдельный тестовый эндпоинт не создавать.
- После успешного входа пользователь возвращается к действию или экрану, который его запросил.
- Гость не имеет профиля и данных на сервере: запросы к защищённым эндпоинтам он не отправляет. Если данные гостя хранятся локально, в плане предложи, нужно ли переносить их в аккаунт после входа (это вне объёма задачи, если усложняет реализацию).
- Состояние сессии явное: `guest` | `authenticated` (и промежуточное `loading` при восстановлении токенов на старте).
- Backend остаётся безопасным по умолчанию: публичные эндпоинты помечаются явно, всё остальное требует токен.

## Этап 
. Keycloak (инфраструктура)
- `docker-compose.yml` в корне репозитория: Keycloak + **один общий контейнер PostgreSQL** для Keycloak и backend (volume для данных). Внутри сервера отдельные базы: `keycloak` для Keycloak и по базе на каждый модуль backend (по правилу архитектуры «своя БД на модуль», в т.ч. для `FitLog.Users`). Таблицы Keycloak и приложения в одной базе не смешиваются.
- Отдельные роли (пользователи) PG: `keycloak` с доступом только к базе `keycloak`, `fitlog` с доступом к базам модулей. Создание ролей и баз: init-скрипт в `docker-entrypoint-initdb.d`, без паролей в репозитории (пароли из `.env`).
- Keycloak стартует после готовности PG (healthcheck + `depends_on: condition: service_healthy`).
- Realm `fitlog` импортируется из JSON (`realm-export`), без секретов и без пользовательских данных.
- Включить: вход по email/паролю, саморегистрацию (registration allowed). Одна роль `user` (realm role), назначается по умолчанию всем новым пользователям. Роль `admin` пока не создаём.
- **Регистрация только по email и паролю:**
  - `registrationEmailAsUsername: true` (email и есть логин, отдельного поля username нет), `loginWithEmailAllowed: true`, `duplicateEmailsAllowed: false`;
  - форма регистрации содержит только email и пароль (+ подтверждение пароля): атрибуты `firstName`/`lastName` в User Profile realm не обязательны и не показываются при регистрации;
  - внешние Identity Providers (Google, GitHub и т.п.) и вход через соцсети не подключаем;
  - подтверждение email (`verifyEmail`) пока выключено (SMTP нет), в плане отметь это как то, что включим позже;
- Клиенты:
  - `fitlog-app`: public client, Standard flow, PKCE S256 обязателен, Direct Access Grants выключен. Redirect URI: схема мобильного приложения и `http://localhost:<порт web>/*`; Web Origins для localhost.
  - `fitlog-swagger`: public client, PKCE, redirect на Swagger UI backend.
- **Offline access** (долгоживущая сессия на мобильных, чтобы пользователя не выкидывало на логин после истечения SSO-сессии):
  - realm role `offline_access` входит в default roles (новые пользователи получают её автоматически);
  - у `fitlog-app` scope `offline_access` в Optional Client Scopes (не Default: клиент запрашивает его явно); у `fitlog-swagger` offline access не нужен;
  - настройки realm: `Offline Session Idle` (например, 30 дней), `Offline Session Max Limited` включён с жёстким максимумом (например, 90 дней), `Revoke Refresh Token` включён (ротация refresh token при каждом обновлении). Конкретные значения предложи в плане.
- Пароли админа и БД только через `.env` (в git только `.env.example`).
- Учесть доступ с Android-эмулятора (`10.0.2.2` или LAN IP) и с web (`localhost`): задокументировать, какой issuer/адрес использовать, чтобы значение claim `iss` совпадало с настройкой backend.

## Этап B. Backend (ASP.NET Core, .NET 10)
- `JwtBearer`: Authority = Keycloak realm, проверка issuer, audience, lifetime. Параметры в конфигурации (`appsettings` + user-secrets / env), без секретов в репозитории.
- Роли из `realm_access.roles` мапятся в `ClaimTypes.Role`; политика авторизации для `user`. Политики и эндпоинты для `admin` не делаем, но механизм ролей оставляем расширяемым.
- Fallback policy требует аутентификации для всех эндпоинтов. Публичные эндпоинты (доступные гостю) помечаются `[AllowAnonymous]` явно. Публичных бизнес-эндпоинтов пока нет, `[AllowAnonymous]` нужен только для технических (например, health, если есть).
- Запрос без токена к защищённому эндпоинту возвращает 401 (не редирект), чтобы клиент мог предложить вход.
- Swagger (Swashbuckle): OAuth2 security scheme (Authorization Code + PKCE, клиент `fitlog-swagger`), кнопка Authorize работает; публичные эндпоинты доступны без авторизации.
- Новый модуль `FitLog.Users` строго по `backend/docs/architecture.md`:
  - своя БД и `DatabaseContext`, строка подключения модуля, `AddUsers(...)` в `DependencyInjection.cs`;
  - сущность профиля: `Id` (= claim `sub`), email, дата создания (имя пока не храним); конфигурация через `IEntityTypeConfiguration<T>`; инварианты через методы сущности;
  - lazy-создание: при первом `GET /users/me` профиль создаётся по claims токена, если его нет;
  - публичный контракт `IUsersModule` и DTO в `FitLog.Shared/Modules/Users/`, чтобы другие модули (Workouts) получали текущего пользователя через интерфейс, без FK и JOIN между модулями;
  - контроллер тонкий, логика в сервисе, чтение через `AsNoTracking()` + проекция в DTO, сущности в ответах API не используются.
- Удобный доступ к текущему пользователю (id из `sub`) через абстракцию из `Shared`, без чтения claims в контроллерах вручную.

## Этап C. Frontend (Expo)
- Библиотека: `expo-auth-session` (+ `expo-web-browser`, `expo-secure-store`, `expo-crypto` при необходимости). Ставить только через `npx expo install`, после установки `npx expo-doctor`.
- Authorization Code + PKCE через discovery документа Keycloak; redirect URI с учётом платформ (Android scheme, web localhost).
- Токены: `expo-secure-store` на мобильных, запасной вариант на web (оцени и предложи в плане: память/sessionStorage, с обоснованием).
- Offline access: на мобильных клиент запрашивает scope `openid profile email offline_access`; полученный offline token хранится только в `expo-secure-store` и используется при старте для восстановления сессии (`loading` → `authenticated`). На web `offline_access` не запрашивается (долгоживущий токен в браузерном хранилище небезопасен), используется обычный refresh token в рамках SSO-сессии. Если считаешь иначе, обоснуй в плане.
- Refresh: автоматический через axios interceptor (один refresh на пачку параллельных 401, повтор запроса после обновления); при провале refresh сессия переходит в `guest`, пользователю показывается предложение войти.
- Axios добавляет `Authorization` только когда сессия `authenticated`. Для гостя запросы к публичным эндпоинтам уходят без токена.
- Сессия: глобальный Zustand-стор в `shared/` (по правилам архитектуры), данные профиля с сервера только в кэше TanStack Query и только для `authenticated`.
- Фича `features/auth/` по структуре frontend-архитектуры: `screens/` (экран входа), `hooks/`, `api/auth.api.ts`, `store/`, `index.ts`. Роуты в `src/app/` только тонкие реэкспорты.
- Доступ к функциям:
  - приложение не закрыто глобальным редиректом на логин;
  - маршруты и экраны только для авторизованных защищены в Expo Router (`Stack.Protected` или группы), гостя вместо ошибки ведут на предложение войти;
  - для отдельных действий и блоков внутри доступных гостю экранов: переиспользуемый компонент `AuthGate` и хук `useRequireAuth` в `shared/`. `AuthGate` рисует `children` для `authenticated` и заглушку с кнопкой входа для гостя (в состоянии `loading` показывает индикатор, а не заглушку); хук выполняет действие или открывает вход и после него возвращает к действию.
  - защищённые маршруты через Expo Router в этой задаче не нужны, пока нет экранов только для авторизованных. Достаточно механизма `AuthGate`; в плане отметь, что именно оставляешь на потом.
- Экран входа, выбор «Продолжить как гость», выход (logout с завершением сессии в Keycloak) на компонентах React Native Paper, цвета из темы. После logout пользователь становится гостем, а не выбрасывается из приложения.
- Logout явно отзывает refresh/offline token (`/protocol/openid-connect/revoke` или logout-эндпоинт с `refresh_token`): offline-сессия не завершается вместе с SSO-сессией. После logout токены удаляются из хранилища.
- Конфигурация адресов Keycloak/API через env Expo (`EXPO_PUBLIC_*`), без хардкода.

## Критерии готовности (ручная проверка)
1. `docker compose up` поднимает общий PG и Keycloak с импортированным realm, админка доступна; в PG созданы база `keycloak` и база модуля Users, роль `keycloak` не видит базы приложения.
2. Приложение запускается без входа. Гость на главном экране видит заглушку «Требуется вход» вместо тестового блока, кнопка «Войти» открывает вход.
3. Регистрация нового пользователя (форма содержит только email и пароль) и вход по email/паролю на web (localhost) и на Android; после входа заглушка заменяется тестовым блоком с данными профиля, пользователь возвращается к запрошенному действию.
4. Запрос к защищённому эндпоинту без токена → 401; с токеном `user` → 200; `[AllowAnonymous]`-эндпоинт без токена → 200.
5. `GET /users/me` при первом вызове создаёт профиль, при повторном возвращает существующий.
6. Swagger UI: Authorize через PKCE → защищённые методы вызываются.
7. Истёкший access token обновляется незаметно для пользователя; после logout пользователь становится гостем, повторные защищённые действия снова требуют вход.
7a. Offline access (Android): после полного перезапуска приложения и истечения SSO-сессии (для проверки уменьшить `SSO Session Max` до нескольких минут) пользователь остаётся `authenticated` без повторного входа. В админке Keycloak у пользователя видна offline-сессия клиента `fitlog-app`; после logout она исчезает. На web offline-сессия не создаётся.
8. `dotnet build FitLog.sln`, `npx tsc --noEmit`, `npx expo lint`, `npx expo-doctor` проходят без ошибок.
9. `architecture.md` обоих проектов обновлены (закрыты открытые решения про аутентификацию, описан гостевой режим), инструкции по запуску Keycloak описаны.
